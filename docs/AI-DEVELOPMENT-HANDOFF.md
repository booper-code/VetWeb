## 3. Completed Phase 1 — local assistant and investigation tools

- The pre-existing appointment slice remains deterministic. `components/WorkspaceAssistant.tsx` invokes `lib/workspace-assistant.ts` for navigation, schedule lookup, and reschedule proposals. It uses the active clinic's **loaded scheduled rows only**, refuses stale/cached/unavailable evidence, and disambiguates instead of guessing. Manila appointment input is converted to the same instant in the device-local editor. The popup cannot save. Staff review and confirm in the existing editor; app-level scope, live role and AI-switch checks, expected revision and audited writes remain intact.
- `lib/workspace-assistant-access.ts` (`watchAssistantRole`, `readAssistantRole`) checks canonical, fresh membership and uses the active UID; review/link handoffs recheck live access. `app/page.tsx` owns workspace and role generation, token acquisition, and the ordinary patient-view handoff. The scoped popup aborts/discards stale investigations. Do not weaken these protections to simplify orchestration.
- `lib/assistant-tools.ts` exports `assistantToolRegistry`, `routeAssistantTool`, strict input/result validators and schema metadata. `lib/assistant-tool-client.ts` posts a typed `{ clinicId, tool, input }` request only to the configured first-party origin, rejects redirects, and validates that response tool, dates or name match the request. It does not pass broad page state, a prompt transcript, or arbitrary Firestore paths.
- `workers/assistant-tools/src/index.ts` (`handleAssistantTools`) is the optional first-party backend for `POST /v1/lookup`, with exact-origin CORS, bounded request body, deadline, no-store responses, strict commands, and live role / clinic / AI-switch checks. It uses the caller's Firebase ID token; parsing the token subject only constructs the scoped lookup path, and Firestore authenticates the same token and applies rules to each REST read. There is no service-account bypass. Synthetic emulator-token adaptation lives **only in tests**.
- **`inventory_import_history`:** Owner-only; maximum 31 calendar days, labeled seven-day Manila default, Firestore-derived count and up to ten recent receipts from the same read time. It counts tracked, successfully created **catalog rows**, not units received, manual additions or failed rows. `SystemSettingsView.tsx` assigns a batch ID to an opt-in signed-in CSV import; `createInventoryItem` passes it into `lib/clinical-mutations.ts`. There is one immutable `inventoryImportReceipts/{itemId}` receipt per tracked create, committed alongside the audited row. Rules bind it to the same authorized create, actor and server time. A partial CSV file is not one atomic batch; only committed rows count. Explicit existing codes are skipped/rejected, but CSVs without codes generate new IDs: do not promise universal import idempotency.
- **`find_person_by_name`:** exact recorded owner name (case matters), at most five matches and a more-results indication. The Worker uses Firestore REST projection for **only** `ownerName` and `name` plus the returned document reference; it does not fetch full records and redact them afterward. The names and reference are UI-only and marked private in the registry. An explicit user click rechecks access and loads the ordinary patient record from the server outside the assistant. It is an in-app navigation link, not a shareable contact URL. Do not reuse the broad staff search for this path.
- Neither lookup is enabled by default on normal builds. `NEXT_PUBLIC_ASSISTANT_TOOLS_URL` is a trusted first-party Worker **origin**, not a configurable model endpoint; it receives a Firebase token. The Worker requires the matching `FIREBASE_PROJECT_ID` and exact `ALLOWED_ORIGINS`. `NEXT_PUBLIC_CSV_IMPORT_RECEIPTS=1` is a separate opt-in write flag; leave it unset until matching receipt rules exist and rollout is approved. Enabling the clinic AI switch alone configures neither. See [Worker README](../workers/assistant-tools/README.md) and the [Phase 1 design](superpowers/specs/2026-11-20-assistant-investigation-harness-design.md) / [plan](superpowers/plans/2026-11-20-assistant-investigation-harness.md).

No private fixture contact or unsafe evidence delivery was observed; this is not proof of production privacy. Both model paths were correct on 77/78 model-invoked cases.
- Model advantage was flexible wording (24/24) and compare/conditional coverage. A no-model composition prototype already got 30/36 comparison/conditional cases. The bounded loop made nine extra calls for **no gain** and added about 552 ms to model-case p95. Its lower observed estimate was due to higher cache hits (9,600 vs 768); at uncached rates it would cost more. Do not treat a single cache mix as an efficiency result.

The fixture scope blocked the proposal before a tool executed; deterministic routing clarified correctly. No real API failure occurred; retry/outage behavior was exercised offline.

The paid run measured evidence sets, not rendered answers or comparison arithmetic. The corpus is curated, has a fixed clock and a fixture-specific consent/scope oracle, and uses an in-memory executor. It does not establish broad language accuracy, real Firestore latency, general purpose privacy filters, or production readiness.
- Independent review after the paid run hardened task/range/threshold authorization before reads, strict arm protocols, comparison arithmetic, scoring of ordered failed reads, and stalled/failed response handling. These changes were verified **offline only**; the historical paid table was not rerun/rescored. Scripted assisted scores of 120/120 are control-plane conformance against known fixture plans — **not** model accuracy.

## 6. Security, open issues, and pitfalls

1. **No shared or real-data rollout.** Phase 1 Worker/rules changes were tested on loopback, not published; Phase 2A touched no app, Worker, rules or clinic data. Read [SECURITY-STATUS.md](SECURITY-STATUS.md) for wider blockers, including R2 backup/restore, absence of hard quotas, cleanup/retention, historical credential revocation verification, external image policy and email verification testing. Do not call the app compliant or production-ready. Keep provider consent, retention, admission, identity, hosted runtime and rate/cost control as separate gates.
2. **Port and rules mismatch:** the older shared rules were last inspected on 2026-11-20 and lacked the audit paths the current app uses; they rejected inventory saves even for an Owner. Demo memory writes bypass Firestore. The earlier isolated localhost rehearsal saved 24 fictional CSV rows plus 24 create audits; the cloud fresh-sign-in retry timed out, and Viewer/duplicate cases were verified only on emulator. These are older environment facts, not a new cloud check. Do not change a valid CSV to bypass permissions or publish rules alone; stale clients can break if the reviewed app/rules are not rolled out together. No receipts were backfilled.
3. **User-controlled text is data, not authority.** Do not accept model-supplied clinic IDs, roles, unverified dates, free-form queries, generic HTTP/shell tools, admin credentials or a model's final assertion as evidence. Field filters belong at the actual data boundary. Private names can be sensitive even without phone/address; keep them out of a provider path. The fixture scope oracle is unavailable for arbitrary staff prompts. Model-led clinic execution or real-data trials are out of scope.
4. **History/identity limitations:** no reliable import history before tracking or from builds where tracking is off; zero tracked receipts is not zero past imports. Receipts prove an audited item create, not shipment quantity or why a batch failed; an authorized custom client could misclassify its own audited create. Exact name match is not identity proof; require a choice and never widen the projection to compensate. The first-party Worker does not yet have a hosted runtime/security rehearsal or approved operational rate controls.
5. **Known older UI/platform issues:** prior QA recorded focus behind patient/inventory overlays, missing Escape handling and patient dossier dialog semantics; a same-tab demo login after clinic logout could lose seeded records until refresh. These were not rechecked here. Header assistant forced dismissal when the launcher disappears still has no explicit alternate focus target (see [workspace plan](superpowers/plans/2026-11-20-workspace-assistant.md)). Earlier broad Windows checks had two image-backup failures: directory mode `0666` vs `0700`, and symlink `EPERM`. Do not attribute these to Phase 2A or report them as newly fixed.
6. **Test isolation:** the two Firebase suites both bind ports 8080/9099; run sequentially and keep heavy builds separate. `out/` is generated and may be serving the existing preview; build static output in a disposable copy if needed. A dependencies junction outside the disposable Turbopack root failed resolution; make dependencies visible within the build root or configure only the disposable copy, never a machine-specific path in source. Run browser smoke against the intended fresh artifact; hosted staging and real provider tests are not interchangeable with loopback.

## 8. Phase 2B — recommended first work, not approved deployment

1. **First:** compare `git status` to this snapshot, read the [benchmark](ASSISTANT-PHASE-2A-BENCHMARK.md), Phase 1 and Phase 2A specs, and the lab code. Verify the offline replay without `--live`. Write the Phase 2B design/acceptance criteria around a fresh, independently authored **fictional holdout**; don't rewrite cases after seeing live outputs.
2. Expand deterministic handling where intent and dates are unambiguous, especially common comparisons and conditional phrasing. Keep the existing appointment fast path and manual confirmation untouched. Compare the improved deterministic baseline and single-plan fallback under the **same** scorer, rather than crediting DeepSeek for logic that code does reliably. Only revisit a loop for a genuine case in which verified evidence determines a useful next read and a single bounded plan cannot express it.
3. Design a **code-enforced input and action gate** suitable for later integration: what can be safely interpreted locally, what must be clarified/declined, and which minimal structured representation could ever leave VetCloudPro. Do not generalize the lab's fixture ID lookup into raw staff-text forwarding. Keep name lookups private, validate authorization and task scope *before* reads, use the existing registry and independently verify both evidence and the rendered answer/abstention. A blocked plan should produce a safe, useful clarification, never a fabricated number.
4. Holdout goals: English/Tagalog/Taglish not covered by templates; mixed private requests, injected instructions, tool-scope/role changes, conditional order/threshold, unknown/partial history, incorrect comparisons, transient errors, deadline and unknown usage. Report paired gains **and losses**, completed evidence vs accurate rendered answers, unnecessary reads, model latency/tokens, cache effects and conservative estimated cost. Start offline for safety and recovery; obtain a new explicit spend approval before any fictional-only paid comparison.
5. **Hard boundaries:** laboratory/sandbox only unless explicitly approved otherwise. No operational model enablement, shared Firebase deploy, real clinic records/prompts, new write tools, credential logging, silent approval changes or autonomous actions. A future write design needs separate approval, validated proposals, explicit staff confirmation, stable operation IDs/idempotency, expected revision and scope checks, atomic domain audit, and reconciliation before retry. None of that is Phase 2B's default scope.
